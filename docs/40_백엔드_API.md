# 40 — 백엔드 API 명세 (구현 후순위 · 스펙 only)

> 상태: Spec v0.1 · 백엔드 **구현은 후순위**, 본 문서는 클라이언트가 의존할 계약(contract)만 정의한다.
> 원칙: 백엔드는 **암호문·메타·동의 증빙만** 다룬다. 다이제스트 평문·콘텐츠·원시 로그는 절대 받지 않는다(CLAUDE.md #1, `docs/50` §1).
> **자산 스토리지 없음** — 응답뱅크·오디오·온디바이스 모델은 앱 번들 내장(OTA·오브젝트 스토리지 불필요).

표기: `🔓`=인증 불필요, `👤`=부모 토큰, `📱`=자녀 기기 토큰(페어링으로 발급).

---

## 1. 인증 (부모 계정)
부모만 계정을 가진다. 자녀 기기는 페어링 시 발급되는 **기기 스코프 토큰**만 사용(자녀가 계정·로그인 다루지 않음).

| Method | Path | 설명 | Auth |
|---|---|---|---|
| POST | `/v1/auth/register` | 부모 계정 생성 | 🔓 |
| POST | `/v1/auth/login` | 로그인 → 액세스/리프레시 토큰 | 🔓 |
| POST | `/v1/auth/refresh` | 토큰 갱신 | 🔓(리프레시) |

---

## 2. 법정대리인 동의 (개인정보 보호법 시행령 §17조의2)
실제 신원확인은 외부 PG/본인인증으로 수행하고, 백엔드는 **동의 확인 *증빙*만 기록**한다.

| Method | Path | 설명 | Auth |
|---|---|---|---|
| POST | `/v1/consent/verify` | 본인인증/결제 콜백 결과로 동의 확인 성립 기록 (어느 호 충족인지 포함) | 👤 |
| GET | `/v1/consent/status` | 동의 유효 여부 조회 (자녀 앱 센싱 게이트가 참조) | 👤 / 📱 |

> 자녀 앱은 센싱 시작 전 `consent/status`로 동의 유효를 확인한다(불변식 #6).

---

## 3. 페어링 = 공개키 교환 (E2EE 부트스트랩)
백엔드는 **공개키 전달만** 돕고 신뢰 근거가 되지 않는다. 진본성은 기기 간 지문 대조로 확보(`docs/50` §1.3).

| Method | Path | 설명 | Auth |
|---|---|---|---|
| POST | `/v1/pairing/initiate` | 부모가 페어링 세션 생성 → 단기 코드/QR 페이로드 반환 | 👤 |
| POST | `/v1/pairing/claim` | 자녀 기기가 코드로 참여 → 📱 토큰 발급 | 🔓(코드) |
| POST | `/v1/pairing/keys` | 각 측이 **X25519 공개키** 등록 | 👤 / 📱 |
| GET | `/v1/pairing/{id}/keys` | 상대 공개키 + 지문 조회(화면 대조용) | 👤 / 📱 |

> 개인키는 어느 엔드포인트로도 전송되지 않는다. Keystore 내부에만 존재.

---

## 4. 다이제스트 중계 (E2EE 암호문 패스스루)
서버는 **암호문 + 라우팅 토큰만** 저장, **복호 불가**, 단기 보존(`docs/50` §1.6).

| Method | Path | 설명 | Auth |
|---|---|---|---|
| POST | `/v1/digests` | 자녀 기기가 E2EE 다이제스트 업로드 `{routing_token, ephemeral_pubkey, nonce, ciphertext, aad}` | 📱 |
| GET | `/v1/digests?since=` | 부모가 미수신 암호문 목록 조회 | 👤 |
| POST | `/v1/digests/{id}/ack` | 부모 수신 확인 → 서버측 정리 트리거 | 👤 |

> 케이스 B(동일 기기)에서는 이 경로를 **건너뛰고** 로컬 전달(`docs/50` §1.8). 본 API는 케이스 A 및 부모 다기기에서만 사용.

---

## 5. 의도적으로 없는 것
- ❌ 콘텐츠/사용 로그 업로드 엔드포인트 — 존재하지 않음(설계상 금지).
- ❌ 다이제스트 복호·분석 엔드포인트 — 서버는 평문을 모름.
- ❌ 자산(오디오/모델) 다운로드 — 번들 내장, 앱 업데이트로 갱신.
